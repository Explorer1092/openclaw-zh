## 1. 检测与分类

我们从以下渠道监控安全信号：

- GitHub 安全公告（GHSA）和私有漏洞报告。
- 当报告不敏感时，公开的 GitHub issues/讨论。
- 自动信号（例如 Dependabot、CodeQL、npm 公告和密钥扫描）。

初始分类：

1. 确认受影响的组件、版本和信任边界影响。
2. 使用仓库 `SECURITY.md` 范围和超出范围规则，将其分类为安全问题与加固/无需处理。
3. 事件负责人相应地做出响应。

## 2. 评估

严重程度指南：

- **严重：** 包/发布/仓库入侵、主动利用，或具有高影响控制或数据暴露的未经认证信任边界绕过。
- **高：** 经过验证的需要有限前提条件的信任边界绕过（例如经过认证但未授权的高影响操作），或 OpenClaw 拥有的敏感凭证暴露。
- **中：** 具有实际影响但可利用性受限或有重大前提条件的重大安全弱点。
- **低：** 纵深防御发现、范围较窄的拒绝服务，或没有已证实的信任边界绕过的加固/奇偶性差距。

## 3. 响应

1. 向报告者确认收到（敏感时私下确认）。
2. 在受支持的发布和最新的 `main` 上重现，然后实施并验证带有回归覆盖的补丁。
3. 对于严重/高级事件，尽快准备修补的发布版本。
4. 对于中/低级事件，在正常发布流程中打补丁并记录缓解指南。

## 4. 沟通

我们通过以下方式沟通：

- 受影响仓库中的 GitHub 安全公告。
- 已修复版本的发布说明/变更日志条目。
- 关于状态和解决方案的直接报告者跟进。

披露政策：

- 严重/高级事件应接受协调披露，在适当时发布 CVE。
- 低风险加固发现可根据影响和用户暴露记录在发布说明或公告中，无需 CVE。

## 5. 恢复和跟进

发布修复后：

1. 在 CI 和发布构件中验证修复。
2. 进行简短的事后审查（时间线、根本原因、检测差距、预防计划）。
3. 添加后续加固/测试/文档任务并跟踪到完成。
