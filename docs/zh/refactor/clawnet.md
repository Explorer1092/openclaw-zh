# Clawnet 重构(协议 + 身份验证统一)

## 目的
单一、严格的文档用于:
- 当前状态: 协议、流程、信任边界。
- 痛点: 批准、多跳路由、UI 重复。
- 提议的新状态: 一个协议、范围角色、统一身份验证/配对、TLS 固定。
- 身份模型: 稳定 ID + 可爱 slug。
- 迁移计划、风险、待解决的问题。

## 目标(来自讨论)
- 所有客户端(mac 应用、CLI、iOS、Android、无头节点)使用一个协议。
- 每个网络参与者经过身份验证 + 配对。
- 角色清晰: 节点 vs 操作员。
- 中央批准路由到用户所在位置。
- 所有远程流量使用 TLS 加密 + 可选固定。
- 最小代码重复。
- 单个机器应该只出现一次(无 UI/节点重复条目)。

## 非目标(明确)
- 移除能力分离(仍然需要最小权限)。
- 在没有范围检查的情况下公开完整网关控制平面。
- 使身份验证依赖于人类标签(slug 仍然是非安全的)。

# 当前状态(现状)

## 两个协议

### 1) 网关 WebSocket(控制平面)
- 完整 API 表面: 配置、通道、模型、会话、代理运行、日志、节点等。
- 默认绑定: 环回。通过 SSH/Tailscale 远程访问。
- 身份验证: 通过 `connect` 的令牌/密码。
- 无 TLS 固定(依赖环回/隧道)。

### 2) Bridge(节点传输)
- 窄允许列表表面、节点身份 + 配对。
- 通过 TCP 的 JSONL;可选 TLS + 证书指纹固定。
- TLS 在发现 TXT 中发布指纹。

## 当前控制平面客户端
- CLI → 通过 `callGateway` 的网关 WS。
- macOS 应用 UI → 网关 WS。
- Web 控制 UI → 网关 WS。
- 浏览器控制使用其自己的 HTTP 控制服务器。

## 当前节点
- 节点模式下的 macOS 应用连接到网关 bridge。
- iOS/Android 应用连接到网关 bridge。
- 配对 + 每个节点令牌存储在网关上。

## 当前批准流程(exec)
- 代理通过网关使用 `system.run`。
- 网关通过 bridge 调用节点。
- 节点运行时决定批准。
- UI 提示由 mac 应用显示(当 node == mac app 时)。
- 节点向网关返回 `invoke-res`。
- 多跳,UI 绑定到节点主机。

## 当前在线状态 + 身份
- 来自 WS 客户端的网关在线状态条目。
- 来自 bridge 的节点在线状态条目。
- mac 应用可以为同一台机器显示两个条目(UI + 节点)。
- 节点身份存储在配对存储中;UI 身份分离。

---

# 问题 / 痛点

- 两个协议栈要维护(WS + Bridge)。
- 远程节点上的批准: 提示出现在节点主机上,而不是用户所在位置。
- TLS 固定仅存在于 bridge;WS 依赖 SSH/Tailscale。
- 身份重复: 同一台机器显示为多个实例。
- 角色不明确: UI + 节点 + CLI 能力未明确分离。

# 提议的新状态(Clawnet)

## 一个协议,两个角色
具有角色 + 范围的单一 WS 协议。
- **角色: 节点**(能力主机)
- **角色: 操作员**(控制平面)
- 操作员的可选**范围**:
  - `operator.read`(状态 + 查看)
  - `operator.write`(代理运行、发送)
  - `operator.admin`(配置、通道、模型)

### 角色行为

**节点**
- 可以注册能力(`caps`、`commands`、权限)。
- 可以接收 `invoke` 命令(`system.run`、`camera.*`、`canvas.*`、`screen.record` 等)。
- 可以发送事件: `voice.transcript`、`agent.request`、`chat.subscribe`。
- 不能调用配置/模型/通道/会话/代理控制平面 API。

**操作员**
- 完整控制平面 API,由范围控制。
- 接收所有批准。
- 不直接执行 OS 操作;路由到节点。

### 关键规则
角色是每个连接的,而不是每个设备的。一个设备可能分别打开两个角色。

# 统一身份验证 + 配对

## 客户端身份
每个客户端提供:
- `deviceId`(稳定,从设备密钥派生)。
- `displayName`(人类名称)。
- `role` + `scope` + `caps` + `commands`。

## 配对流程(统一)
- 客户端未经身份验证连接。
- 网关为该 `deviceId` 创建**配对请求**。
- 操作员收到提示;批准/拒绝。
- 网关发放绑定到以下内容的凭证:
  - 设备公钥
  - 角色
  - 范围
  - 能力/命令
- 客户端持久化令牌,经过身份验证重新连接。

## 设备绑定身份验证(避免承载令牌重放)
首选: 设备密钥对。
- 设备生成一次密钥对。
- `deviceId = fingerprint(publicKey)`。
- 网关发送 nonce;设备签名;网关验证。
- 令牌发放给公钥(所有权证明),而不是字符串。

替代方案:
- mTLS(客户端证书): 最强,更多运维复杂性。
- 短期承载令牌仅作为临时阶段(尽早轮换 + 撤销)。

## 静默批准(SSH 启发式)
精确定义以避免薄弱环节。首选一种:
- **仅本地**: 当客户端通过环回/Unix socket 连接时自动配对。
- **通过 SSH 挑战**: 网关发出 nonce;客户端通过获取它来证明 SSH。
- **物理存在窗口**: 在网关主机 UI 上进行本地批准后,允许在短时间窗口内自动配对(例如 10 分钟)。

始终记录 + 记录自动批准。

# 到处都是 TLS(开发 + 生产)

## 重用现有 bridge TLS
使用当前 TLS 运行时 + 指纹固定。

## 应用于 WS
- WS 服务器支持使用相同证书/密钥 + 指纹的 TLS。
- WS 客户端可以固定指纹(可选)。
- 发现为所有端点发布 TLS + 指纹。
  - 发现仅是定位器提示;从不是信任锚。

## 为什么
- 减少对 SSH/Tailscale 的机密性依赖。
- 默认情况下使远程移动连接安全。

# 批准重新设计(集中化)

## 当前
批准发生在节点主机(mac 应用节点运行时)上。提示出现在节点运行的位置。

## 提议
批准是**网关托管的**,UI 交付给操作员客户端。

### 新流程
1) 网关接收 `system.run` 意图(代理)。
2) 网关创建批准记录: `approval.requested`。
3) 操作员 UI 显示提示。
4) 批准决定发送到网关: `approval.resolve`。
5) 如果批准,网关调用节点命令。
6) 节点执行,返回 `invoke-res`。

### 批准语义(加强)
- 广播到所有操作员;只有活动 UI 显示模态(其他得到 toast)。
- 第一个解决方案获胜;网关拒绝后续解决为已解决。
- 默认超时: N 秒后拒绝(例如 60 秒),记录原因。
- 解决需要 `operator.approvals` 范围。

## 好处
- 提示出现在用户所在位置(mac/手机)。
- 远程节点的一致批准。
- 节点运行时保持无头;无 UI 依赖。

# 角色清晰示例

## iPhone 应用
- **节点角色**用于: 麦克风、相机、语音聊天、位置、push-to-talk。
- 可选 **operator.read** 用于状态和聊天视图。
- 可选 **operator.write/admin** 仅在显式启用时。

## macOS 应用
- 默认情况下为操作员角色(控制 UI)。
- 启用"Mac 节点"时的节点角色(system.run、screen、camera)。
- 两个连接的相同 deviceId → 合并的 UI 条目。

## CLI
- 始终为操作员角色。
- 范围由子命令派生:
  - `status`、`logs` → read
  - `agent`、`message` → write
  - `config`、`channels` → admin
  - 批准 + 配对 → `operator.approvals` / `operator.pairing`

# 身份 + slug

## 稳定 ID
身份验证所需;永不改变。
首选:
- 密钥对指纹(公钥哈希)。

## 可爱 slug(龙虾主题)
仅人类标签。
- 示例: `scarlet-claw`、`saltwave`、`mantis-pinch`。
- 存储在网关注册表中,可编辑。
- 碰撞处理: `-2`、`-3`。

## UI 分组
跨角色的相同 `deviceId` → 单个"实例"行:
- 徽章: `operator`、`node`。
- 显示能力 + 最后一次看到。

# 迁移策略

## 阶段 0: 文档 + 对齐
- 发布此文档。
- 盘点所有协议调用 + 批准流程。

## 阶段 1: 向 WS 添加角色/范围
- 使用 `role`、`scope`、`deviceId` 扩展 `connect` 参数。
- 为节点角色添加允许列表门控。

## 阶段 2: Bridge 兼容性
- 保持 bridge 运行。
- 并行添加 WS 节点支持。
- 在配置标志后面控制功能。

## 阶段 3: 中央批准
- 在 WS 中添加批准请求 + 解决事件。
- 更新 mac 应用 UI 以提示 + 响应。
- 节点运行时停止提示 UI。

## 阶段 4: TLS 统一
- 使用 bridge TLS 运行时为 WS 添加 TLS 配置。
- 向客户端添加固定。

## 阶段 5: 弃用 bridge
- 将 iOS/Android/mac 节点迁移到 WS。
- 保持 bridge 作为回退;稳定后移除。

## 阶段 6: 设备绑定身份验证
- 对所有非本地连接要求基于密钥的身份。
- 添加撤销 + 轮换 UI。

# 安全说明

- 在网关边界执行角色/允许列表。
- 没有客户端在没有操作员范围的情况下获得"完整"API。
- 所有连接都需要配对。
- TLS + 固定降低移动设备的 MITM 风险。
- SSH 静默批准是一种便利;仍然记录 + 可撤销。
- 发现从来不是信任锚。
- 能力声明由平台/类型针对服务器允许列表进行验证。

# 流式传输 + 大有效负载(节点媒体)
WS 控制平面适用于小消息,但节点也执行:
- 相机片段
- 屏幕录制
- 音频流

选项:
1) WS 二进制帧 + 分块 + 反压规则。
2) 单独的流端点(仍然 TLS + auth)。
3) 对媒体繁重的命令保持 bridge 更长时间,最后迁移。

在实施前选择一个以避免漂移。

# 能力 + 命令策略
- 节点报告的 caps/commands 被视为**声明**。
- 网关执行每个平台的允许列表。
- 任何新命令都需要操作员批准或显式允许列表更改。
- 使用时间戳审计更改。

# 审计 + 速率限制
- 日志: 配对请求、批准/拒绝、令牌发放/轮换/撤销。
- 速率限制配对垃圾信息和批准提示。

# 协议卫生
- 显式协议版本 + 错误代码。
- 重新连接规则 + 心跳策略。
- 在线状态 TTL 和最后一次看到语义。

# 待解决的问题

1) 运行两个角色的单个设备: 令牌模型
   - 建议每个角色单独的令牌(节点 vs 操作员)。
   - 相同的 deviceId;不同的范围;更清晰的撤销。

2) 操作员范围粒度
   - read/write/admin + approvals + pairing(最小可行)。
   - 稍后考虑每个功能的范围。

3) 令牌轮换 + 撤销 UX
   - 角色更改时自动轮换。
   - UI 按 deviceId + 角色撤销。

4) 发现
   - 扩展当前 Bonjour TXT 以包括 WS TLS 指纹 + 角色提示。
   - 仅作为定位器提示。

5) 跨网络批准
   - 广播到所有操作员客户端;活动 UI 显示模态。
   - 第一个响应获胜;网关强制原子性。

# 摘要(TL;DR)

- 今天: WS 控制平面 + Bridge 节点传输。
- 痛点: 批准 + 重复 + 两个堆栈。
- 提议: 一个具有显式角色 + 范围的 WS 协议、统一配对 + TLS 固定、网关托管批准、稳定设备 ID + 可爱 slug。
- 结果: 更简单的 UX、更强的安全性、更少的重复、更好的移动路由。
