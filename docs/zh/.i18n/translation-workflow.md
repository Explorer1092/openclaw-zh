# 翻译工作流

文档发布流程的内部说明。本文件位于 `docs/.i18n` 下，该目录被文档站点构建忽略，不会发布。

## 目标

- 英文文档在每次源文档同步后迅速部署。
- 语言翻译不在每次热门 `main` 提交时运行。
- 翻译工作会去抖处理，以便一批文档提交只产生一次翻译波。
- 语言 Job 仅翻译自上次成功语言输出以来源哈希发生变化的页面。
- 成功的语言输出会一起提交，即使一个或多个语言 Job 失败。
- 每周协调运行会重新运行每个语言/页面路径，以修复遗漏或偶发失败的翻译。

## 事件流

1. `openclaw/openclaw` 将英文文档同步到 `openclaw/docs`。
2. GitHub Pages 立即从同步提交中部署英文/源变更。
3. `Translate All` 由同步提交、发布分发、手动分发或每周计划触发。
4. 协调器在开始翻译前等待一个冷却窗口。
5. 冷却后，协调器读取当前 `origin/main` 的源元数据。
6. 如果在冷却期间有更新的文档同步到达，协调器使用更新的源状态。
7. 每语言翻译 Job 以 `fail-fast: false` 并行运行。
8. 每个语言 Job 为请求的源 SHA 上传一个产物。
9. 最终处理器下载可用产物，忽略过时或失败的 payload，并推送一个聚合 i18n 提交。
10. 聚合提交落地后，最终处理器分发一次 Pages 部署。
11. Pages 工作流在部署后分发实时烟雾测试。

## 去抖策略

协调器在文档同步或发布分发后等待 1 小时，然后重新读取 `origin/main`。

默认冷却时间由发布仓库变量 `OPENCLAW_DOCS_TRANSLATION_COOLDOWN_SECONDS` 控制，默认值为 `3600`。Repository dispatch 调用者可以通过 `client_payload.cooldown_seconds` 覆盖，手动运行可以设置 `cooldown_seconds`。

如果在等待期间 `.openclaw-sync/source.json` 发生变化，则从较新的状态重新等待。如果 `main` 持续变化，等待时间以 `OPENCLAW_DOCS_TRANSLATION_MAX_WAIT_SECONDS` 为上限（默认值等于冷却值）。超过上限后，翻译最新观察到的状态。

手动运行和每周运行默认不等待。

## 增量翻译

每个翻译页面存储 `x-i18n.source_hash`。语言 Job 将当前英文页面哈希与存储的语言哈希进行比较。

普通运行仅翻译：

- 缺失的语言页面
- `x-i18n.source_hash` 过时的语言页面
- 受源文件删除/清理影响的页面

`docs/.i18n/**` 下的内部文件不是翻译输入。仅更改内部 i18n 文件的推送触发运行会在语言矩阵之前跳过。

如果某个语言 Job 失败，其产物被标记为失败且不携带 payload。最终处理器仍然提交成功的语言。失败的语言仍然过时，并在下一次增量运行中被处理，因为其源哈希仍然不匹配。

## 产物契约

每个语言 Job 上传一个以语言和源 SHA 命名的产物：

```text
i18n-zh-cn-<source-sha>
```

产物内容：

```text
metadata.json
changed-files.txt
deleted-files.txt
payload/docs/<locale>/**
payload/docs/.i18n/<locale>.tm.jsonl
```

`metadata.json` 包括语言、语言 slug、源 SHA、待处理数量、变更数量以及任何失败原因。最终处理器会拒绝 `source_sha` 与当前 `.openclaw-sync/source.json` 不匹配的产物。

源仓库发布工作流分发一个 `translate-all-release` 事件。协调器仍接受旧的每语言发布事件以保持兼容性，但这些只是后备方案。

## 聚合提交

最终处理器在正常路径中拥有唯一的语言推送。

提交消息：

```text
chore(i18n): refresh translations
```

该提交可能包含部分语言集。Job 摘要列出已应用的语言、无变更的语言、缺失或失败的语言、过时产物和无效产物。

## 每周协调

每周运行使用 `full` 模式。它强制对每种语言和每个源页面进行完整协调，而不是仅依赖变更的源哈希。

词汇表更改也会强制完整协调，因为词汇表指导会影响源哈希未变更的页面。

预期行为：

- 重新生成或验证每个语言页面
- 清理过时的语言页面
- 根据需要刷新翻译记忆库
- 仍使用并行语言 Job
- 仍提交一个聚合结果
- 仍容忍单个语言失败

每周运行是修复 LLM 偶发性、部分失败和遗漏增量更新的机制。

## 部署策略

英文从源同步提交部署。

翻译在聚合 i18n 提交后部署。最终处理器分发一次 GitHub Pages，因为 GitHub 会抑制来自 `GITHUB_TOKEN` 提交的普通推送触发工作流运行。Pages 工作流在部署后分发实时烟雾测试，以便烟雾测试检查已部署的站点而不是与部署竞争。

文档繁忙的一天应该会产生许多快速的英文部署，但只有少量的语言部署。

如果外部部署提供商（如 Mintlify）监听每次推送，聚合 i18n 提交就是降低负载的手段。避免恢复对 `main` 的每语言推送。
