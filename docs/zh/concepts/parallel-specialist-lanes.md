并行专家通道让一个 Gateway 将不同的聊天或房间路由到不同的 Agent，同时保持用户体验的流畅。关键在于将并行性视为稀缺资源设计问题，而不仅仅是"更多 Agent"。

## 第一原则

只有在减少真实瓶颈竞争时，专家通道才能提升吞吐量：

- **Session 锁**：每次只有一个运行可以修改给定的 Session。
- **全局模型容量**：所有可见聊天运行仍共享 Provider 限制。
- **工具容量**：Shell、浏览器、网络和仓库工作可能比模型轮次本身更慢。
- **上下文预算**：长对话记录会使每次未来轮次都变慢且不够专注。
- **所有权模糊**：重复的 Agent 做相同的工作会浪费容量。

OpenClaw 已通过[命令队列](/concepts/queue)对每个 Session 的运行进行序列化，并限制全局并行度。专家通道在此之上添加策略：哪个 Agent 拥有哪些工作、什么留在聊天中、什么变成后台工作。

## 推荐的推广方式

### 第一阶段：通道契约 + 后台重型工作

在每个通道的工作区和系统提示中写下契约：

- **目的**：该通道负责的工作。
- **非目标**：应该转交的工作。
- **聊天预算**：快速解答留在聊天中；长任务应简短确认，然后在后台子 Agent 或任务中运行，完成后返回结果。
- **移交规则**：当另一个通道拥有该请求时，说明应该去哪里，并提供精简的移交摘要。
- **工具风险规则**：优先使用能完成任务的最小工具接口。

这是成本最低的阶段，能修复大多数阻塞问题：一个编码任务不再使研究通道陷入停滞，每个聊天保持其自己的上下文干净。

### 第二阶段：优先级和并发控制

根据每个通道的业务价值调整队列和模型容量：

```json5
{
  agents: {
    defaults: {
      maxConcurrent: 4,
      subagents: { maxConcurrent: 8, delegationMode: "prefer" },
    },
  },
  messages: {
    queue: {
      mode: "collect",
      debounceMs: 1000,
      cap: 20,
      drop: "summarize",
    },
  },
}
```

对高优先级工作使用私信/个人聊天和生产运维 Agent。当系统繁忙时，让研究、起草和批量编码任务转移到后台任务。

### 第三阶段：协调器/交通控制器

当多个通道活跃后，添加小型协调器模式：

- 追踪活跃通道任务和所有者。
- 检测跨群组的重复请求。
- 在通道之间路由移交摘要。
- 只呈现阻塞、已完成结果和必须由人做出的决策。

不要从这里开始。没有通道契约的协调器只是协调混乱。

## 最小通道契约模板

```md
# 通道契约

## 负责

- <该通道负责的工作>

## 不负责

- <需要移交的工作>

## 聊天预算

- 直接回答简单问题。
- 对于多步骤、缓慢或工具密集型工作：简短确认，派生/后台执行工作，完成后返回结果。

## 移交

如果另一个通道拥有该请求，回复：

- 目标通道
- 目标
- 相关上下文
- 确切的下一步行动

## 工具姿态

使用能完成任务的最小工具接口。避免广泛的 Shell 或网络工作，除非该通道明确负责此类工作。
```
